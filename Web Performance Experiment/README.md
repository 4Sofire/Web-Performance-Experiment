# Web Performance Experiment — CST3990

**A Controlled Experimental Evaluation of Front-End and Back-End Factors Affecting Web Page Performance**

---

## 1. Project Overview

This project conducts a controlled experimental evaluation of nine web performance factors using a **One-Factor-At-a-Time (OFAT)** methodology. Each factor is varied independently while all others are held at a defined baseline, and performance is measured using Google Lighthouse across six standardised metrics.

**Core academic contribution:** controlled factor isolation at the individual level — no prior study has systematically varied individual front-end and back-end factors independently under controlled conditions.

**Factors tested:** 5 front-end (F1–F5) and 4 back-end (B1–B4)  
**Configurations:** 18 OFAT + 3 combined = 21 total  
**Runs per configuration:** 50  
**Total audits:** 1,050  
**Metrics:** TTFB, FCP, Speed Index, LCP, TBT, CLS

## 4. First-Time Setup

Follow these steps in order. Do not skip any step.

**Step 1 — Install dependencies**
```bash
npm install
```

**Step 2 — Configure environment**
```bash
copy .env.example .env
```
Open `.env` in a text editor and set your MySQL password:
```
DB_HOST=localhost
DB_USER=root
DB_PASSWORD=yourpassword
DB_NAME=webperf_experiment
PORT=3000
```

**Step 3 — Seed the database**

Mac/Linux:
```bash
mysql -u root -p < db-setup.sql
```

Windows — locate your `mysql.exe` file and run:
```bash
"<path-to-your-mysql.exe>" -u root -p < db-setup.sql
```
Example: `"C:\Program Files\MySQL\MySQL Server X.X\bin\mysql.exe"`
Not sure where it is? Search for `mysql.exe` in File Explorer.


**Step 4 — Generate assets**
```bash
npm run setup
```
This creates all images, JavaScript payload files, and CSS files in `public/`.

**Step 5 — Run the benchmark** (two terminals)

Terminal 1 — keep this open for the entire session including Steps 8 and 9:
```bash
npm start
```

Terminal 2:
```bash
npm run benchmark
```
The benchmark runs 18 configurations × 50 runs = 900 audits. Estimated time: 3.5–4 hours.

After each configuration completes all 50 runs, a per-configuration summary is printed showing the mean values of all six metrics, followed by the total elapsed time for that configuration.

If the benchmark is interrupted (e.g. computer sleeps or terminal closes), simply run `npm run benchmark` again — it will automatically detect completed configurations and resume from where it stopped.

**Step 6 — Analyse results**
```bash
npm run analyse
```
This produces statistics for the 18 OFAT configurations only. If combined CSVs from a previous benchmark session exist in the results folder, they will be skipped automatically with a message explaining why. This is expected behaviour — proceed to Steps 7 and 8 to generate new combined results.

**Step 7 — Build combined configurations (RQ5)**
```bash
npm run build-combined
```

**Step 8 — Run combined benchmark** (keep server running in Terminal 1)
```bash
npm run benchmark-combined
```
This adds 3 × 50 = 150 audits. Estimated time: ~45 minutes.

**Step 9 — Final analysis**
```bash
npm run analyse
```
Results are now in `results/`.

## 6. Between Benchmark Runs

To clear results without touching assets or the database:

```bash
npm run clean
```

It is recommended to run `npm run clean` before each new full benchmark session. This ensures that the results folder contains only data from the current session and prevents any ambiguity in the analysis output caused by result files from previous sessions.

## 8. Output Files Explained

All files are saved to `results/` with a timestamp in the filename.

### results-TIMESTAMP.csv
Raw Lighthouse audit rows from the OFAT benchmark. One row per audit run. Used by `analyse.js` to build master-results.csv.

### results-combined-TIMESTAMP.csv
Raw Lighthouse audit rows from the combined benchmark (3 configurations × 50 runs = 150 rows). Kept separate from OFAT results so `npm run analyse` can never accidentally overwrite combined data. Only a combined CSV with a timestamp later than the most recent OFAT CSV will be picked up by `npm run analyse`. If the combined CSV predates the OFAT CSV, it will be skipped automatically.

### timing-TIMESTAMP.txt
Per-configuration duration and total runtime for the OFAT benchmark.

### timing-combined-TIMESTAMP.txt
Per-configuration duration and total runtime for the combined benchmark.

### master-results.csv
All raw Lighthouse audit rows. One row per audit run.

| Column | Description |
|--------|-------------|
| factor | Factor ID (e.g. F1, B3, COMBINED_FULL) |
| label | Configuration name |
| run | Run number (1–50) |
| ttfb_ms | Time to First Byte in milliseconds |
| fcp_ms | First Contentful Paint in milliseconds |
| speed_index_ms | Speed Index in milliseconds |
| lcp_ms | Largest Contentful Paint in milliseconds |
| tbt_ms | Total Blocking Time in milliseconds |
| cls | Cumulative Layout Shift (dimensionless) |
| audit_duration_ms | Total time Lighthouse took for that audit |
| config_duration_s | Elapsed time for the configuration so far |
| url | Full URL used for the audit |

Rows: 900 after OFAT, 1,050 after combined benchmark.

### descriptive-stats-TIMESTAMP.csv
One row per configuration. Per metric: mean, median, SD, 95% CI, min, max, IQR, skewness.

### inferential-stats-TIMESTAMP.csv
One row per configuration. Per metric: Welch's t-test t-statistic, degrees of freedom, p-value, significance flag (Yes/No at α=0.05), mean difference from baseline.

### summary-TIMESTAMP.csv
Human-readable overview. Key metrics (TTFB, FCP, LCP) with mean, SD, CI95, difference from baseline, and significance.

## 9. Experimental Design

### Research Questions

- **RQ1:** What is the relative influence of selected front-end and back-end factors on web page performance metrics under controlled experimental conditions?
- **RQ2:** Can an automated benchmarking system reliably detect and demonstrate performance differences under controlled testing conditions?
- **RQ3:** Which front-end factors have the greatest impact on page loading speed and client-side performance metrics?
- **RQ4:** Which back-end factors have the most significant effect on server response time and content delivery performance?
- **RQ5:** Do the combined front-end and back-end performance improvements outperform the sum of their individual effects?

### Factors and Levels

| ID | Domain | Factor | Levels |
|----|--------|--------|--------|
| F1 | Front-end | JavaScript Payload Size | 0KB / 100KB / 500KB / 1000KB |
| F2 | Front-end | Render-Blocking Resources | 0 / 1 / 3 stylesheets |
| F3 | Front-end | Image Format | JPEG / WebP / AVIF |
| F4 | Front-end | Image Lazy Loading | Disabled / Enabled |
| F5 | Front-end | Code Splitting | Single bundle / Split chunks |
| B1 | Back-end | Server Processing Delay | 0ms / 200ms / 500ms / 1000ms |
| B2 | Back-end | Database Query Complexity | None / Simple / Complex join |
| B3 | Back-end | Caching Configuration | Disabled / Enabled |
| B4 | Back-end | Response Compression | None / Gzip / Brotli |

### Baseline Configuration
```
f1=0, f2=0, f3=jpeg, f4=disabled, f5=single, b1=0, b2=none, b3=disabled, b4=none
```

### OFAT Configuration Count
- 1 baseline + 3 (F1) + 2 (F2) + 2 (F3) + 1 (F4) + 1 (F5) + 3 (B1) + 2 (B2) + 1 (B3) + 2 (B4) = **18 OFAT configurations**

### Combined Configurations (RQ5)
Three additional configurations generated automatically by `npm run build-combined`:
1. Best 2 front-end factors combined
2. Best 2 back-end factors combined
3. All 4 best factors combined

### Metrics and Good Thresholds

| Metric | Good Threshold | Primary Use |
|--------|---------------|-------------|
| TTFB | ≤ 800ms | Back-end factors |
| FCP | ≤ 1800ms | General load |
| Speed Index | ≤ 3400ms | General load |
| LCP | ≤ 2500ms | Primary metric (both domains) |
| TBT | ≤ 200ms | JavaScript blocking |
| CLS | ≤ 0.1 | Layout stability |

## 10. Important Rules

These rules must not be broken — doing so will invalidate the experimental results or cause errors on Windows.

- **Never hardcode `--remote-debugging-port=9222`** — the port is extracted dynamically from `browser.wsEndpoint()`
- **Never use chrome-launcher** — replaced by Puppeteer due to Windows EPERM errors on temp file writing
- **Never add throttling to Lighthouse config** — this is a controlled local test; throttling introduces uncontrolled variability
- **Never add external CSS files to the test page** — all page styling must be inline CSS; external stylesheets would alter the F2 (render-blocking) variable
- **Never merge old complete CSV runs with new incomplete ones** — the smart merge logic in analyse.js handles this automatically
- **Never edit combined-config.js manually** — it is auto-generated by `npm run build-combined`

## 11. Troubleshooting

### MySQL not recognised on Windows
Locate your `mysql.exe` file and use its full path:
```bash
"<path-to-your-mysql.exe>" -u root -p < db-setup.sql
```
Not sure where it is? Search for `mysql.exe` in File Explorer, or check `C:\Program Files\MySQL\` for your installed version folder (e.g. MySQL Server 8.0, MySQL Server 9.6).

### EPERM or temp file errors
This project uses Puppeteer instead of chrome-launcher specifically to avoid Windows EPERM errors. If you see EPERM errors, ensure you are running `npm run benchmark` (not any script that uses chrome-launcher directly).

### Lighthouse fails to connect
Ensure the server is running in a separate terminal (`npm start`) before running any benchmark command. Check `http://localhost:3000/health` returns `{"status":"ok"}`.

### `combined-config.js` not found
Run `npm run analyse` first, then `npm run build-combined`. The combined-config.js is auto-generated and requires a completed descriptive-stats CSV to exist.

### AVIF images not generated
Some platforms do not support AVIF encoding in the version of libvips bundled with sharp. The setup script automatically falls back to WebP for the AVIF file. Results will still be valid — the file size difference will be minimal.

### Out of memory during benchmark
The benchmark runs Lighthouse audits sequentially (one at a time) with an 800ms pause between runs. If memory issues occur, restart the benchmark — the smart resume logic will pick up from where it stopped.

### "Combined CSV(s) found but all predate the current OFAT run"
This message appears when `npm run analyse` finds a combined results file from a previous benchmark session that is older than the current OFAT results file. This is expected and not an error. It means the combined benchmark has not yet been run for the current session. Proceed with `npm run build-combined` followed by `npm run benchmark-combined`, then run `npm run analyse` again.
